**Goal:** prove that the IDE can build an exact **source line ↔ absolute address** table from NASM's listing and
map output, for the program shapes beginners write.

**Scope (in):**
- A .NET 10 console project that runs the local NASM 3.02 with the R-ASM flags (`-f bin --before "cpu 8086"
  --before "[map all …]" -l … -Xgnu --reproducible`), using an argument list and a temporary directory.
- Parsers for the listing (line, section-relative offset, bytes, continuation lines, inline errors) and the map
  (section Vstart). A mapping function: absolute address = offset + section Vstart.
- Fixtures in `poc/POC-002-source-mapping/fixtures/`:
  1. single section;
  2. `.text` + `.data` (with alignment);
  3. `times` and `align`;
  4. a multi-line `%macro`;
  5. `%include` of a second file;
  6. a source with errors;
  7. a source containing `cpu 386`, to exercise the bypass detection idea.
- Verification: compare each mapped address with the bytes at that offset in the `.com` output (and with `ndisasm`).
- Diagnostics parser for the GNU format, including `info:` and `[-w+class]`.

**Out of scope:** UI, debugger integration, MZ output.

**Exit criteria (results recorded here as `[Measured]`):**
1. Every instruction line in fixtures 1–5 maps to the correct address (verified against the binary).
2. A documented answer for macros, `times` and `%include` (supported / limitation and workaround).
3. Errors (fixture 6) are parsed with correct lines and severities.
4. A proposed detection approach for the `cpu` directive (fixture 7) with its limitations.
5. Verdict: listing + map is **sufficient / sufficient with limitations / insufficient**.

## Results (2026-10-26 18:42 +0500, Claude Code)

**Environment [Measured]:** Windows 11 Pro, NASM 3.02 (`nasm.exe`, `ndisasm.exe` on PATH), .NET SDK 10.0.403, Release build.
**Code:** `poc/POC-002-source-mapping/`: `Poc.Mapping` (safe NASM runner, GNU diagnostics parser, listing and map parsers,
`SourceMap`, independent verifiers) and `Poc.Mapping.Tests` (xUnit v3, MTP mode). Fixtures in `fixtures/` (7 + `inc/helpers.inc`).

Three **independent** verifiers run on each buildable fixture (01–05):
1. every known listing byte equals the `.com` byte at the mapped address;
2. every label's map-file symbol address equals the mapped address of its line;
3. every mapped code range starts on an instruction boundary according to `ndisasm -b 16`.

### Exit criteria
1. **Every instruction line in fixtures 1–5 maps to the correct address: yes.** All three verifiers pass, plus explicit expectations
   (e.g. 01: line 4 → 0100h, line 8 ↔ 010Ch; 02: `.data` from the map, re-entered `.text` continues at 010Fh; 05: `newline` → `inc/helpers.inc` line 3).
2. **Macros, `times`, `%include`:**
   - `times` / `align`: **supported.** One listing row with `<rep Nh>` covers the full length (e.g. `times 5 nop` → 0102h, 5 bytes).
     A no-op `align` in `.data` shows no bytes.
   - Macros: **supported.** Expanded rows are marked `<n>`, but **their line numbers are the macro-definition lines**, not the invoking line.
     The mapper attributes them to the invoking line (what the user wrote), flagging `FromMacroExpansion`. Macro definition lines get no address.
   - `%include`: **supported.** Included rows use the same `<n>` marker **at the same column (36)** as macro rows, with line numbers
     restarting in the included file. The two are told apart by context (a preceding `%include` row). Paths are resolved against NASM's
     working directory (the main file's folder), with the includer's folder as fallback.
3. **Errors parsed correctly: yes.** GNU format `file:line: error|warning|info: message [-w+class]` (3 diagnostics in fixture 6 with lines,
   severities, warning class). On failure, **no image is written, the map file is created but empty, and the listing is still written**
   with inline `******************  error: …` rows.
4. **CPU-directive bypass detection: proposed and demonstrated.** `nasm -E` normalizes every `cpu` directive to `[cpu <level>]`,
   **including one hidden inside a macro**. Scanning the preprocessed output detects the bypass (fixture 7 and a hidden-macro case).
   Cost: build 66–83 ms, `-E` 62–67 ms (6 runs each, this machine), about 140 ms total, inside NFR-006.
   Alternative [Hypothesis]: scan the listing's source column (macro expansions are listed too) to avoid the second process.
5. **Verdict: listing + map is _sufficient with limitations_** for source ↔ address mapping (OQ-009).

### Limitations and notes for the architecture phase
- The listing column layout is **undocumented** by NASM. It was measured on 3.02, so pin the NASM version and keep these fixtures as regression tests.
- Nesting markers `<10>` and deeper (four characters) may shift columns. Not tested [Unverified].
- Nested includes from subdirectories: NASM path resolution is not tested beyond one level [Unverified].
- `%rep` blocks and `section` directives emitted from inside macros are not covered by fixtures [Unverified].
- Relocated values appear in brackets (`BA[0000]`) as section-relative placeholders. The final bytes come from the image, not the listing.
- The safe runner works as designed: no shell, argument list, per-build temp directory, a 1 s timeout kills a hung stub process
  (test passes), output cap 1 MiB.
